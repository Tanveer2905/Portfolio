CASE_FILE: LOCAGO

> cat cases/locago.md

[ INTERNSHIP, DISTRICT ADMINISTRATION, TEHRI GARHWAL · JUN–AUG 2024 ]

> the problem

The district's police, fire and ambulance vehicles already carried GPS trackers, but from more than one vendor, each with its own API and response format. The job was to put one fleet view on top of those feeds, and get the nearest unit moving toward a caller as fast as possible.

> how it works

caller ── service type + GPS ──┐
                               v
tracker A ──┐         ┌─────────────────┐
            ├─ norm ─>│    Flask app    │──> PostgreSQL
tracker B ──┘         │  dispatch core  │    fleet + GPS history
                      └────────┬────────┘
                               │ candidate units
                               v
                     OSRM: road km + ETA
                               │ nearest unit
                               v
                     Twilio SMS ──> driver

The driver's SMS carries the caller's coordinates, a map link and their phone number.

> key decisions

  • Road distance, not straight line. In Tehri the roads follow the valleys. A unit 2 km away across a ridge can be 30 minutes further than one 6 km down the road, so candidates are ranked by OSRM driving distance and ETA. Slower to compute, but the assignments are actually right.
  • Accept both tracker formats. Instead of asking vendors to standardise, ingestion detects which schema a feed uses and pulls the fields it needs from either.
  • Derive stops at query time. A gap of 120 seconds or more between readings counts as a stop. The write path stays simple, and the threshold can change without reprocessing history.

> impact

  • EST.~80–90% faster to raise an emergency request with the one-click flow
  • EST.~30–50% faster response from nearest-unit routing

These figures are estimates, not controlled measurements.

> what I'd do next

  • Push live positions over WebSockets instead of polling
  • Fetch trackers concurrently and prefilter by bounding box before routing, so dispatch stays fast as the fleet grows
  • Add authentication with separate dispatcher and admin roles

CASE_FILE: AETHERMATH

> cat cases/aethermath.md

[ SOURCE PRIVATE · WALKTHROUGH ON REQUEST ]

> the problem

LLMs can sound completely confident about a math problem and still get it wrong. For a student, a wrong answer explained well is worse than no answer. AetherMath splits the work across specialised agents so a solution gets checked before anyone sees it.

> how it works

text  /  image  /  audio
  │
  ├─ parser ····· turns the input into a clean problem
  ├─ solver ····· works it, with retrieved context (FAISS)
  ├─ verifier ··· checks the solution before it ships
  ├─ explainer ·· writes the step-by-step walkthrough
  │
  └─> memory ···· SQLite + similarity search,
                  improved by human feedback

> key decisions

  • One job per agent. Parsing, solving, verifying and explaining are separate steps, so a mistake in one can be caught by the next instead of flowing straight to the user.
  • Meet students where they are. A problem can come in as typed text, a photo of a worksheet, or spoken audio.
  • A memory that gets better. Solved problems are stored with similarity search, and human-in-the-loop feedback shapes what the system learns from.

CASE_FILE: HIREMIND

> cat cases/hiremind.md

[ OPEN SOURCE · RUNS FULLY OFFLINE ]

> the problem

Screening a pile of resumes against a job description is slow, and most AI tools for it want candidate data uploaded to someone else's cloud. HireMind does the ranking on your own machine: no API keys, nothing leaves the laptop.

> how it works

PDF resumes + job description
  │
  ├─ parse ······· pdfplumber + spaCy, ~500-skill taxonomy
  ├─ embed ······· BGE-base 768-d vectors ──> FAISS
  ├─ score ······· 5-factor weighted + must-have filters
  ├─ rerank ······ LLaMA 3 8B, local, optional
  ├─ personalize · LightGBM on recruiter decisions
  │
  └─> ranked shortlist ──> CSV / Excel

> the score

FactorWeightHow
Semantic similarity35%Cosine similarity, resume vs. JD embeddings
Skill match25%Taxonomy-aware, with aliases
Experience relevance20%Sigmoid centred on the JD's requirement
Recency10%Exponential decay, recent work weighs more
Keyword precision10%Coverage of the JD's top 30 keywords

> key decisions

  • Local-first. The LLM runs in-process (Q4-quantized LLaMA 3 8B via llama-cpp-python), so candidate data never touches a third-party API.
  • The LLM is optional. Without enough RAM or a GPU it falls back to an algorithmic evaluator that still writes candidate-specific analysis. Nothing breaks.
  • Learn the recruiter's taste. After 20+ shortlist/reject decisions, a LightGBM model adjusts scores by up to ±10%, and it persists across sessions.
  • Cache every stage. Parsed resumes, embeddings and LLM evaluations are saved to disk, so re-runs on the same pile are fast.

> also in the box

  • Chat search: "who has both React and Docker?" becomes structured filters
  • Per-candidate interview questions
  • Multi-tenant FastAPI backend with JWT auth and per-user FAISS indexes
  • Self-contained Docker image with models baked in

CASE_FILE: SCAN

> cat cases/scan.md

[ B.TECH MAJOR PROJECT · MAY 2025 ]

> the problem

A photo of a sick leaf should tell you what the disease is, and also show where the model was looking, so a wrong answer is easy to spot. The people using a tool like this usually can't verify a diagnosis on their own.

> how it works

leaf photo (web upload / Android camera)
  │
Flask /predict_api
  ├─ classify ··· 128×128 input
  │     CNN, ResNet50, MobileNetV2, VGG16
  │     SVM, XGBoost, Random Forest (on CNN features)
  │     └─> majority vote of 7
  ├─ segment ···· rembg background removal ──> U-Net mask
  ├─ histogram ·· RGB distribution (OpenCV)
  │
  └─> JSON: each model's label, final label, mask, histogram

> results

PlantVillage: 54,000 images, 38 classes, 14 crops. 70/15/15 split.

ModelAccuracyF1
CNN (custom)98.0%93%
MobileNetV297.0%94%
SVM97.0%94%
ResNet5095.8%95.5%
VGG1695.0%95%
XGBoost93.0%88%
Random Forest88.0%85%
Majority vote ensemble96.1%—

Segmentation: Dice 0.872, IoU 0.812.

The ensemble doesn't beat the best single model on raw accuracy. What it buys is stability on look-alike classes such as tomato early vs. late blight, where one model's blind spot shouldn't become the final answer.

> key decisions

  • Seven models, one vote. CNNs, tree ensembles and a margin classifier fail in different ways, so an error has to be shared by four of seven to reach the user.
  • Classical models on learned features. SVM, XGBoost and Random Forest train on CNN features instead of hand-made ones. SVM reaches 97% this way.
  • Segmentation as explainability. A confident label with a mask over healthy tissue is a signal to distrust the prediction.
  • Remove the background first. Field photos include soil, hands and other leaves, so rembg isolates the target leaf before the U-Net runs.

> what I'd do next

  • On-device inference with TensorFlow Lite or ONNX for offline use in the field
  • Evaluate on real field photos; PlantVillage is shot under controlled lighting
